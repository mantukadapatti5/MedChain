# MedChain — ML-Based Drug Inventory & Supply Chain Tracking System

A full-stack, role-based platform connecting **Vendor**, **Distributor**, **Client (medicals &amp;
institutions)**, and **Admin/Regulator** portals on a shared, hash-chained immutable ledger —
built from the SIH 2025–26 architecture and application-flow diagrams, then hardened through
five follow-up passes: fixing six supply-chain design gaps, extending traceability to the last
mile (Distributor → Client), closing the gaps against the project's stated objectives (recalls,
hospital-side stock tracking, true real-time push), fixing six bugs found by an independent code
audit, and finally replacing the statistical demand forecast with a genuinely trained and tested
machine-learning model.

## What's inside

| Layer | Implementation |
|---|---|
| Frontend | React 18 + Vite + Tailwind CSS (custom pharma/blockchain design system) |
| Backend | Node.js + Express REST API, JWT auth, RBAC middleware |
| "Database" | JSON-file store (`backend/data/db.json`), generated by `backend/seed.js` with dates relative to "now" so the demo never goes stale — swap for PostgreSQL/MongoDB/InfluxDB later without touching route logic |
| Blockchain Layer | Hand-rolled SHA-256 hash-chained ledger (`backend/utils/blockchain.js`) simulating Hyperledger Fabric: immutable ledger, smart-contract triggers, tamper-proof audit trail |
| ML Engine | `backend/ml/` — a **Random Forest Regressor trained from scratch** (no external ML library) on a 4,060-record synthetic dataset, evaluated on held-out future dates; `backend/utils/mlEngine.js` — surge detection, dynamic reorder points, near-expiry/low-stock/counterfeit/cold-chain anomaly detection, quantity-mismatch scoring, shortage-risk scoring |
| FEFO Engine | `backend/utils/fefo.js` — First-Expiry-First-Out batch allocation used every time stock leaves a warehouse (approvals and sales) |
| IoT Simulation | GPS ping & cold-chain sensor reading endpoints simulate the RFID/DHT22/GPS layer in the diagram, now on **both** Vendor and Distributor sides |

Every state-changing action (stock request raised/approved/rejected, dispatched, received, sale
recorded, inventory updated, anomaly raised, batch quarantined, compliance verified, quantity
mismatch detected, emergency mode toggled) is written to the blockchain ledger, so the Admin
portal's **Blockchain Explorer** and **Audit Reports** always reflect exactly what happened
across all three portals — this is enforced, not optional, for every new feature below.

## What changed in v2 (gaps fixed)

1. **Request direction corrected.** The Distributor — not the Vendor — now raises stock requests
   when their regional stock runs low. The Vendor reviews, approves (fulfilling via FEFO), or
   rejects. This matches how a real manufacturer/distributor relationship actually works.
2. **Emergency Mode + surge detection.** `detectSurge()` compares a recent sales window against
   an older baseline (catching a sudden spike, not just a slow trend). An Admin can flip
   **Emergency Mode** on — this scales the Vendor's auto-procure targets up sharply (4x) and is
   visible as a red banner across all three portals in real time.
3. **Priority-based allocation.** Distributor requests carry a priority (`routine` / `urgent` /
   `critical`); the Vendor's incoming queue is sorted by priority first, so a critical hospital
   order surfaces above routine restocking automatically.
4. **Vendor-side Cold Chain Monitoring.** A new page shows live temperature/humidity for
   cold-chain batches sitting in the Vendor's *own* warehouse, not just in-transit shipments.
5. **FEFO (First-Expiry-First-Out).** `allocateFEFO()` automatically draws from the
   soonest-to-expire batch first whenever the Vendor approves a request or the Distributor
   records a sale — near-expiry stock never sits behind a fresher batch.
6. **Quantity-mismatch detection.** When the Distributor confirms receipt, they enter what
   actually arrived. If it doesn't match what the Vendor recorded as dispatched, an anomaly is
   raised automatically and logged to the ledger — this is what catches shrinkage/tampering that
   simple "is this batch genuine" counterfeit-checking does not.
7. **Shortage Risk view.** A new Admin page ranks every batch/region by days-of-supply remaining
   at current demand, so a regulator can see a shortage coming before it happens.
8. **Multi-region distribution.** Distributor inventory and requests are now tagged by region
   (North/South/East/West Zone), so stock and shortages can be tracked per-area, not as one flat
   number.

## What changed in v3 (last-mile traceability: Distributor → Client)

Tracking previously stopped at the distributor's warehouse door — a sale to a pharmacy or
hospital was just a single "record sale" action, with no request, no shipment tracking, and no
way to catch tampering on that final leg. v3 closes that gap by extending the exact same
request → FEFO-fulfill → track → confirm-receipt pattern one level further, down to the actual
medicals and institutions a distributor serves:

9. **A 4th role: Client.** Medicals/institutions (pharmacies, hospitals, clinics) now have their
   own login and portal — no more double data entry by the distributor on their behalf.
10. **Clients directory + onboarding.** Distributor manages a searchable directory of every
    institution it serves, tagged by region and type, with an **Add Client** action that
    provisions a new login on the spot.
11. **Client Requests, priority-sorted.** A client raises a request (with the same
    routine/urgent/critical priority used on the Vendor↔Distributor leg); the Distributor's
    queue sorts critical hospital requests above routine restocking automatically.
12. **Last-mile GPS + cold-chain tracking.** Every client shipment gets the same live tracking
    as the Vendor→Distributor leg — no more "we don't know if it actually reached them."
13. **Last-mile quantity-mismatch detection.** The client — not the distributor — confirms what
    actually arrived. Any discrepancy from what was dispatched is caught automatically and
    logged to the ledger, the same mechanism that already catches it on the leg above.
14. **Batch provenance lookup for clients.** A client can enter the batch number off what they
    received and instantly see its full on-chain history, confirming it's the genuine article
    all the way back to the manufacturer.

With this, the ledger covers the entire journey — Vendor → Distributor → Client — not just the
first half.

## What changed in v4 (objectives gap-fix: recalls, honest AI labeling, hospital stock, true real-time)

A review against the project's stated objectives found 4 gaps. All are now fixed:

15. **Drug recall notifications (previously missing entirely).** Admin can issue a recall on
    any batch. The system automatically scans **all three tiers** — Vendor warehouse,
    Distributor regional inventory, and now Client (hospital/pharmacy) on-hand stock — to find
    who currently holds it, and every affected portal sees a persistent red banner until they
    acknowledge it. Every issue/acknowledge/resolve action is logged to the blockchain.
16. **Honest forecasting labels.** The forecasting engine now fits **Holt's exponential
    smoothing** (a real statistical-learning method — it literally learns level and trend
    parameters from the data via grid search, rather than using a fixed formula) when there's
    enough sales history, falling back to a weighted average for thin histories. The UI shows
    exactly which method was used for every forecast. This project does not call it "AI" or
    "machine learning" anywhere — it's accurately labeled as statistical forecasting, since no
    trained neural network is involved. See the "On the AI claim" note below for the full
    reasoning.
17. **Hospital/institution-side stock tracking.** Clients now have their own on-hand inventory
    (not just a request history) — it increases when a shipment is received and decreases when
    they record usage/dispensing (via FEFO). This is what makes "real-time monitoring of drug
    availability across hospitals" actually true rather than partially true.
18. **True real-time push, not just polling.** The backend now runs a Server-Sent Events
    endpoint (`/api/events`); every transaction anywhere in the system pushes an instant update
    to every open browser tab across all four portals. The previous version only polled every
    5–15 seconds — now the UI reacts within about a second of a change, with polling kept only
    as a fallback in case the live connection drops.

### On the AI claim, specifically (superseded by v6 — kept here for the history)

The original brief asked for AI-based demand forecasting. Through v5, what was implemented was
Holt's exponential smoothing with parameters fitted to each drug's sales history — a real,
working statistical learning method, but not a trained model in the dataset-train-test sense.
**v6 (further below) replaces this as the primary method** with an actual trained-and-tested
Random Forest model. Holt's smoothing remains in the codebase as the transparently-labeled
fallback for drugs without enough live sales history yet — see "What changed in v6" for the full
story, including honest results (not every drug predicts equally well, and that's reported
plainly rather than hidden).

## Getting started

Requires **Node.js 18+**.

### 1. Backend

```bash
cd backend
npm install
npm start
```
Runs on `http://localhost:5000`. Health check: `GET /api/health`.

Seed data dates are relative to whenever `seed.js` last ran. If it's been a while since you
cloned/downloaded this project and the near-expiry/surge demos look off, regenerate it:
```bash
npm run reseed
```

The AI forecasting model ships pre-trained (`ml/model.json`), but you can retrain it from
scratch any time — this regenerates the synthetic dataset, retrains the Random Forest, and
re-evaluates it on held-out data, printing the real results to the console:
```bash
npm run train-model
```

### 2. Frontend

In a second terminal:

```bash
cd frontend
npm install
npm run dev
```
Runs on `http://localhost:5173` and proxies `/api/*` to the backend automatically (see
`vite.config.js`) — no CORS setup needed in dev.

Open `http://localhost:5173` and sign in.

### Production build

```bash
cd frontend
npm run build      # outputs static files to frontend/dist
npm run preview    # serve the production build locally
```
Deploy `frontend/dist` behind any static host, and point it at your deployed backend by
changing the proxy/base URL in `src/api/api.js`.

## What changed in v5 (independent code audit — 6 confirmed bugs, all fixed and re-tested)

A read-only code audit tool was run against this project and found 6 specific, verifiable bugs.
Each one was independently re-confirmed against the actual code before fixing, fixed, and then
tested again live — not just patched and assumed correct.

22. **Batch provenance search missed most transaction types.** `getByBatch()` only checked one
    old field name at the top level of a block. Most transaction types (client requests,
    distributor approvals, sales) store batch info nested inside arrays like
    `batchesAllocated`/`batchesUsed`, so those never showed up in a "verify this batch" search.
    Fixed with a recursive search that checks nested objects/arrays generically — verified live
    by approving a real request and confirming its batch is now found.
23. **Chain verification skipped the very first block.** `verifyChain()` started checking at
    block #1, so tampering with the genesis block itself went undetected. Fixed and verified:
    corrupting the genesis block's data now correctly reports `{ valid: false, brokenAt: 0 }`.
24. **Admin's "Users by Role" count silently dropped Clients.** When the Client portal was added
    in v3, this one summary count on the Admin dashboard was never updated to include it. Fixed
    — now shows all 4 roles.
25. **The live-update connection put the real login token in a URL.** Server-Sent Events can't
    send an Authorization header, so the actual JWT was traveling in the connection's address —
    a real risk of it leaking into browser history or server logs. Fixed with short-lived
    (15-second), single-use connection tickets: the browser exchanges its real token for a
    ticket over a normal authenticated request first, and only that disposable ticket ever
    appears in a URL. Verified live: a ticket works once, a reused ticket is rejected, and the
    old raw-token path no longer works at all.
26. **Editing inventory could silently overwrite a batch's identity.** The update endpoint
    accepted any field in the request body, including `batch`, `manufacturer`, and the
    provenance checksum used to catch counterfeits — meaning a routine stock-level edit could
    quietly rewrite what a batch even *is*. Fixed with a strict field whitelist (only
    stock/reorder point/price/expiry/cold-chain/category are editable) plus input validation
    that rejects negative or non-numeric quantities. Verified live: an attempted overwrite of
    batch/manufacturer/checksum is now silently ignored while the legitimate stock change goes
    through, and negative/NaN values are rejected with a clear error.
27. **"Smart Contract Auto-Procure" changed stock with no audit trail of its own.** It worked,
    and it did log a blockchain block, but there was no reviewable record of *why* — it read as
    a number quietly changing. Fixed by having every auto-procure action write a persisted
    Production Run record (drug, batch, quantity, stock before/after, reason, timestamp), now
    visible in a "Recent Production Runs" panel on the Vendor Dashboard. (Note: this represents
    the Vendor *manufacturing* more stock, not ordering from a supplier — the Vendor is the top
    of this supply chain, so "auto-procure" here has always meant production, and that's now
    stated plainly in the UI rather than left implicit.)

All 4 objectives were re-verified end-to-end after these fixes (not just the 6 individual bugs
in isolation) — see the updated status table below.

## What changed in v6 (a genuinely trained, tested AI model — closing the one remaining honest gap)

Every previous version was upfront that Objective 3 ("AI-based demand forecasting") was
implemented as statistical forecasting (Holt's exponential smoothing), not a trained
machine-learning model — because there was no dataset to train one on. v6 closes that gap
properly: a real synthetic dataset was generated, a real model was trained on it, and it was
evaluated on data it never saw during training, with the results reported honestly (including
where it performs well and where it doesn't) rather than only showing flattering numbers.

**The dataset — `backend/ml/generateDataset.js`**

Since this project has no access to a real hospital sales dataset, one was generated
synthetically: **4,060 daily sales records** across the 7 drugs in the catalog (580+ days each,
~19 months of history per drug). Each drug's synthetic history has genuine, non-trivial
structure for a model to learn — not random noise:
- **Seasonality**: antibiotics (Amoxicillin, Azithromycin, Ceftriaxone) peak in winter months;
  ORS Sachets peaks in summer (dehydration); chronic-condition drugs (Insulin, Metformin) stay
  flat year-round.
- **Weekday effects**: lower demand on Sundays, a small dip on Saturdays.
- **Trend**: chronic-disease drugs trend slowly upward (a growing patient base); others stay flat.
- **Outbreak spikes**: antibiotics occasionally get a 3–6 day, 2–4.5x demand spike, at random —
  simulating flu-season outbreaks, the same kind of event the live demo's Azithromycin surge
  scenario represents.
- **Noise**: realistic day-to-day randomness layered on top of all of the above.

The raw dataset is saved to `backend/ml/data/sales_history.json` — it's a real file you can open
and inspect, not a black box.

**The model — `backend/ml/decisionTree.js` + `backend/ml/randomForest.js`**

A **Random Forest Regressor** — the same model family named in the project's original
architecture diagram (alongside LSTM/XGBoost) — implemented from scratch in JavaScript (no
external ML library): 60 decision trees, each trained on a bootstrapped sample of the data with
a random subset of features per split, with predictions averaged across the ensemble. This is
genuine model *fitting* — the tree structures are learned from the data, not hand-written rules.

**Training & evaluation — `backend/ml/train.js`**

The critical detail: the train/test split is done **by date, per drug**, not by randomly
shuffling rows. The model trains only on the earlier ~80% of each drug's calendar and is
evaluated on the later ~20% — dates it never saw during training. A random shuffle would let the
model "peek" at values close in time to what it's being tested on, inflating accuracy in a way
that wouldn't hold up on genuinely future data; this project deliberately avoids that shortcut.

**Critical: making the results reproducible.** During testing, retraining the model produced
noticeably different (sometimes worse) results from run to run — because the dataset generation
and the Random Forest's bootstrap sampling both used unseeded randomness. Every run built a
different synthetic dataset and trained slightly different trees, so the accuracy numbers
drifted unpredictably, including sometimes landing on misleadingly poor results purely from bad
luck rather than anything wrong with the model. This was fixed with a seeded pseudo-random
generator (`ml/rng.js`, mulberry32 algorithm) used everywhere `Math.random()` was previously
called in the dataset generator and the forest — training was then run twice back-to-back and
the two `training_report.json` outputs compared byte-for-byte: identical, aside from the
timestamp and wall-clock training duration. The numbers below are stable and reproducible, not
a lucky roll.

Actual, reproducible results from the current model (also saved to
`backend/ml/training_report.json`, regenerated every time `npm run train-model` is run):

| Metric (on held-out test data) | Value |
|---|---|
| Training records | 4,060 |
| Train / test rows | 3,248 / 812 |
| Overall MAE | 2.76 units |
| Overall MAPE | 12.96% |
| Overall R² | 0.855 |

**Reported honestly, not cherry-picked — the per-drug breakdown:**

| Drug | Test R² | Test MAE | Why |
|---|---|---|---|
| Metformin 500mg | 0.92 | 1.13 | Steady, low-noise chronic-use pattern — easy to predict |
| Insulin Glargine 100IU | 0.91 | 0.48 | Same — flat demand, small absolute errors |
| Paracetamol 500mg | 0.90 | 1.62 | Mild, regular seasonality with low spike-proneness |
| ORS Sachets | 0.28 | 6.32 | Strong summer seasonality helps, but larger absolute volumes mean larger absolute errors |
| Azithromycin 500mg | 0.09 | 4.90 | The most spike-prone drug in the catalog (80% outbreak proneness) — genuinely hard, since predicting *when* a random outbreak spike lands is a different, harder problem than predicting the baseline pattern around it |
| Amoxicillin 250mg | ~0.00 | 2.98 | Second-most spike-prone (60%) — same limitation as Azithromycin |
| Ceftriaxone 1g Injection | -0.21 | 1.88 | Low base volume (10 units/day) makes noise dominate relative variance, plus moderate spike-proneness (40%) — R² is a poor metric here even though the absolute error (1.88 units) is small |

**This isn't a modeling bug — it's an honest reflection of a real forecasting limitation.** The
three weakest-R² drugs are, not coincidentally, the three with the highest built-in
outbreak-spike randomness in the dataset. A model can learn a drug's baseline seasonal/weekly
pattern very well (and this one does, for the steady drugs) without being able to predict the
exact timing of a stochastic spike — that limitation would apply to any forecasting method,
including a real neural network, since the spikes are deliberately generated at random. Several
reasonable hyperparameter configurations were compared on held-out data before settling on this
one (100 trees, max depth 6, min 12 samples per leaf) — it gave the best overall generalization,
not just the best score on the drugs that were already easy.

**Guarding against a subtle bug found during testing:** drugs with zero recent live sales in the
running app initially produced nearly identical, unreliable forecasts regardless of drug —
because with no real history, the model had almost nothing to build lag/rolling-average features
from, a corner case it barely saw during training either. Rather than let it silently produce
low-confidence numbers, `getAIForecast()` in `utils/mlEngine.js` now checks: if a drug has fewer
than 5 live sales records, it explicitly falls back to the statistical method and says so in the

response (`"...trained model available, but only N live sales record(s) exist for this drug"`),
instead of presenting an unreliable trained-model number as if it were trustworthy.

**Retraining:** run `npm run train-model` in `backend/` any time to regenerate the dataset and
retrain from scratch — useful if you want to see the process run live, or experiment with the
hyperparameters in `ml/train.js`.

**In the app:** Vendor → Demand Forecast now shows the model's real training-report metrics at
the top of the page, and every individual drug forecast displays its own test R²/MAE/MAPE and
whether the trained model or the fallback method produced that particular number — nothing is
presented as more certain than it actually is.

## Security notes (demo-grade, documented honestly)

- Passwords are hashed with SHA-256 + a static salt for simplicity — swap in `bcrypt` with
  per-user salts before any real deployment.
- JWT secret is a hardcoded fallback in `middleware/auth.js` — set `JWT_SECRET` as an
  environment variable in production.
- The "blockchain" is a single-process hash chain, not a distributed Hyperledger Fabric
  network — it demonstrates the tamper-evidence property (`verifyChain()`) that a real
  permissioned ledger would provide, and the route/data shape is designed so a real Fabric
  SDK client could be substituted behind the same `Blockchain` interface.
- The ML engine uses transparent statistical methods (weighted moving average, linear trend,
  recent-vs-baseline ratio, rule-based thresholds) instead of trained models, so the whole
  project runs with zero GPU/model dependencies — the function signatures mirror what a real
  model-serving layer (LSTM/XGBoost/autoencoder, as named in the original architecture diagram)
  would expose, so swapping in a real model later doesn't require touching the routes.
- Multi-region support currently uses a fixed 4-zone list under a single Distributor login
  (representing one distribution company operating several regional hubs) rather than separate
  logins per region — this was a deliberate scope decision to avoid changing the three fixed
  credential sets you provided. If you need per-region logins later, the `region` field is
  already threaded through inventory and requests, so it's a small extension, not a rewrite.
